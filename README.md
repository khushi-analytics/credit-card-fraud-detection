# Credit Card Fraud Detection — Imbalanced Classification

A end-to-end machine learning project for detecting fraudulent credit card transactions, built with the real-world constraints of financial services in mind — severe class imbalance, banking-specific evaluation metrics, model explainability for regulatory compliance, and a champion-challenger deployment framework.

---

## Business context

Credit card fraud is a rare event problem. In this dataset, only **0.17% of transactions are fraudulent** — meaning a model that classifies every single transaction as legitimate achieves 99.83% accuracy while catching zero fraud cases. This is the accuracy paradox, and it is why standard machine learning evaluation metrics are misleading for fraud detection.

This project is built around the actual decisions a data scientist would make when building a fraud detection model inside a regulated financial institution:

- Why precision-recall AUC is the right primary metric, not accuracy or ROC-AUC
- Why class weights are preferred over SMOTE in a banking context
- Why the decision threshold is a business decision, not a modelling decision
- Why SHAP explainability is a requirement, not an optional extra
- Why the evaluation framework mirrors a champion-challenger deployment process

## What this project covers

### 1. Exploratory Data Analysis
- Class imbalance visualisation — illustrating why accuracy is misleading
- Transaction amount and time-of-day distribution by fraud vs legitimate
- Feature correlation analysis to identify the strongest predictors of fraud

### 2. Preprocessing and Feature Engineering
- Log transformation of transaction amount to reduce the effect of extreme values
- **Chronological train-test split** — the most important preprocessing decision in this project. Random splitting leaks future transactions into the training set, which artificially inflates performance metrics. In production, a fraud model only ever sees past data, so the evaluation must reflect that by using the most recent 20% of transactions as the test set.

### 3. Baseline model — Logistic Regression with class weights
Logistic Regression is the correct starting point for a fraud model in a regulated bank because it is:
- Fully interpretable (coefficients have direct, explainable meaning)
- Fast enough for real-time transaction scoring
- Preferred by model risk validation teams for its transparency
- A meaningful performance benchmark that every subsequent model must beat

### 4. Imbalance handling — Class weights vs SMOTE

Two approaches are compared:

**Class weights** (`class_weight='balanced'`): tells the model to penalise misclassifying the minority class more heavily. No synthetic data is created.

**SMOTE** (Synthetic Minority Oversampling Technique): generates synthetic fraud examples by interpolating between existing fraud cases.

**Why class weights are preferred in banking:** Synthetic fraud transactions may not reflect the actual behaviour patterns of real fraudsters. In a regulated environment, the training data should reflect the real world as closely as possible. Class weights achieve the same imbalance correction without introducing artificial data points that could mislead the model on novel fraud patterns.

### 5. Main model — XGBoost
XGBoost is the industry standard for tabular fraud data. Key configuration choices:
- `scale_pos_weight` set to the ratio of legitimate to fraud transactions (~577) — the XGBoost-native way to handle imbalance
- `eval_metric='aucpr'` — optimises directly for precision-recall AUC rather than accuracy
- L1 and L2 regularisation to prevent overfitting on the minority class
- Early stopping on a validation set to find the optimal number of trees

### 6. Evaluation — banking-relevant metrics

| Metric | Why it matters in fraud detection |
|---|---|
| **Precision-Recall AUC** | Primary metric. Informative when positive class is rare. Not dominated by the majority class like ROC-AUC. |
| **KS Statistic** | Standard banking model validation metric. Measures the maximum separation between the cumulative distribution of fraud and legitimate scores. KS > 0.4 indicates good discrimination. |
| **Recall at operating threshold** | The fraction of actual fraud cases the model catches. Missing a fraud case (false negative) is typically costlier than a false alarm. |
| **Precision at operating threshold** | The fraction of flagged transactions that are actually fraudulent. Affects investigation team workload. |
| ROC-AUC | Reported for completeness but less informative than PR-AUC for severely imbalanced data. |

**Accuracy is not reported.** A model predicting all transactions as legitimate would achieve 99.83% accuracy. Reporting accuracy for an imbalanced fraud problem is misleading and not used in practice.

### 7. Threshold analysis — a business decision, not a modelling decision

The classification threshold (default 0.5) determines the trade-off between recall and precision. This project explicitly demonstrates that **the threshold is set by the business, not the modeller**, based on:
- How many alerts the fraud investigation team can review per day
- The relative cost of missing a fraud case vs generating a false alarm
- The severity and reversibility of the fraud type being detected

The notebook shows the operational impact (alerts generated, fraud caught, false alarms) at every possible threshold so the business can make an informed decision about where to operate.

### 8. SHAP explainability

In regulated financial services, model risk management teams require that individual predictions can be explained. SHAP (SHapley Additive exPlanations) attributes each feature's contribution to a specific prediction.

Three SHAP visualisations are produced:
- **Summary bar plot** — global feature importance across all predictions
- **Beeswarm plot** — shows the direction and magnitude of each feature's effect
- **Waterfall plot** — explains a single individual prediction (what a fraud investigator would see when asking "why was this transaction flagged?")

### 9. Champion-challenger framework

In production banking environments, models are never simply replaced. A challenger model is run in parallel on a portion of traffic alongside the live champion model, with systematic performance comparison before any promotion decision is made. This project simulates that process by evaluating both the baseline Logistic Regression (champion) and XGBoost (challenger) on the same held-out test set using consistent metrics.

## Key design decisions

Every major decision in this project has a documented justification rooted in real-world banking practice rather than textbook defaults:

**Why chronological split, not random?**  
Fraud data is time-ordered. A random split allows future transactions to appear in the training set, which is a form of data leakage that inflates performance metrics and does not reflect how the model would behave in production.

**Why PR-AUC as the primary metric?**  
ROC-AUC is dominated by the true negative rate when the negative class is overwhelming. For a dataset with 0.17% fraud, a poor model can achieve a high ROC-AUC by doing well on the majority class. PR-AUC focuses specifically on performance on the minority class — the one that actually matters.

**Why class weights over SMOTE?**  
Both techniques address class imbalance. SMOTE creates synthetic fraud examples which may not reflect the actual statistical properties of real fraud. In a regulated banking context where model training data needs to be as representative of the real world as possible, class weights are the cleaner and more defensible approach.

**Why report KS statistic?**  
KS statistic is the standard performance metric used by model risk validation teams in UK banks. It measures the maximum separation between the cumulative distribution of fraud and legitimate scores — a higher KS indicates the model does a better job of ranking fraud above legitimate. Reporting it here reflects how models are actually evaluated in a production banking environment.

**Why SHAP?**  
PRA Supervisory Statement SS1/23 on Model Risk Management requires that models deployed in UK banks can be explained and challenged. SHAP provides the mechanism to explain individual predictions to fraud investigators, risk managers, and regulators.

## Limitations and future work

- **Features are PCA-transformed** — the original transaction features are not available due to confidentiality, which limits domain-specific feature engineering (velocity features, geographic anomalies, device fingerprints) that would be available in a real fraud system
- **Static dataset** — does not demonstrate concept drift monitoring (PSI, model performance degradation over time), which is a critical part of production fraud model maintenance
- **No real-time scoring pipeline** — a production system would include a feature store, model serving API, and latency benchmarking
- **Two-day snapshot** — the dataset covers only two days of transactions, limiting the ability to build time-based behavioural features

Future extensions: adding a model monitoring section that simulates concept drift, building a Streamlit dashboard for real-time threshold adjustment, and extending to include a population stability index (PSI) tracker.
